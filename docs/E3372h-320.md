# Huawei E3372h-320 reference

Findings from bringing up the E3372h-320 with ModemManager. Verified on
firmware `10.0.3.1(H192SP1C983)`, hardware `CL4E3372HM`, WebUI
`10.0.3.1(W13SP2C7110)`, on a Raspberry Pi 5. The [README](../README.md) covers
installation and the port layout; this document covers the rest.

## USB modes

| USB ID | Mode | How it gets there |
|---|---|---|
| `12d1:1f01` | Storage (virtual CD-ROM) | After power-on or a firmware reboot |
| `12d1:14db` | HiLink: the stick is a router with NAT at `192.168.8.1`, `cdc_ether` | HuaweiNew message (`usb_modeswitch -J`), what usb-modeswitch-data sends |
| `12d1:155e` | Modem: AT ports and NCM | HuaweiAlt message (`usb_modeswitch -X`, `HuaweiAltMode=1`), what this package sends |

The switch isn't stored; the stick comes back as `12d1:1f01` after every power
cycle or firmware reboot. Unlike the E3372h-153, the -320 can't be reflashed to
"stick" firmware, and it doesn't have to be: the HuaweiAlt message is enough.

The package's `/etc/usb_modeswitch.d/12d1:1f01` overrides usb-modeswitch-data's
entry for this ID. usb-modeswitch's dispatcher has a global switch for the same
effect (`HuaweiAltModeGlobal=1` in `/etc/usb_modeswitch.conf`), which would also
affect other Huawei IDs; the package doesn't use it.

## Modem mode interfaces

| If | Class | Function | Driver | ModemManager |
|---|---|---|---|---|
| 0 | `ff/02/01` | AT / PPP | `option` (`ttyUSB0`) | PPP port |
| 1 | `ff/02/03` | Diagnostics | `option` (`ttyUSB1`) | not used ("unhandled port type") |
| 2 | `ff/02/02` | AT | `option` (`ttyUSB2`) | primary port |
| 3 | `02/0d/00` | NCM control | `cdc_ncm` (`wwan0`) | data port |
| 4 | `0a/00/01` | NCM data | `cdc_ncm` | – |

The kernel's `option` driver knows Huawei's vendor-class interfaces, and the
port types come from the class/subclass/protocol rules in ModemManager's
`77-mm-huawei-net-port-types.rules` (unchanged by this package). No extra udev
rules are needed.

## Data connection

ModemManager's Huawei plugin dials with `^NDISDUP` and reads the address from
`^DHCP?`; NetworkManager configures `wwan0` statically (e.g. `10.0.2.63/8`,
gateway `10.0.0.1`). The NCM link comes up properly, unlike on the E3372-325.

If ModemManager goes away without disconnecting (crash, SIGKILL), the
connection stays active in the stick (`^NDISSTATQRY: 1,...`), and
`^NDISDUP=1,1` then answers `ERROR`. Debian's Huawei plugin keeps retrying
that until NetworkManager gives up; the stick only recovers when it's power
cycled or gets `AT^NDISDUP=1,0`. Patch 0004 checks `^NDISSTATQRY?` before
dialing and disconnects such a leftover connection first. A clean
ModemManager stop disconnects properly, with or without the patch.

IPv4 and IPv4v6 bearers both work. With IPv4v6 the bearer reports an IPv6
configuration via DHCP; the tested carrier (Melita IoT roaming on O2 Germany)
didn't provide a global IPv6 address.

## Rebooting the stick from HiLink mode

In HiLink mode there's no AT port, and on the Pi 5 `uhubctl` re-enumerates the
stick without cutting its power, so it stays in HiLink mode. The HiLink web API
can reboot it (it then comes back as `12d1:1f01` and gets switched again):

```sh
R=$(curl -s http://192.168.8.1/api/webserver/SesTokInfo)
S=$(echo "$R" | sed -n 's:.*<SesInfo>\(.*\)</SesInfo>.*:\1:p')
T=$(echo "$R" | sed -n 's:.*<TokInfo>\(.*\)</TokInfo>.*:\1:p')
curl -s -X POST http://192.168.8.1/api/device/control \
  -H "Cookie: $S" -H "__RequestVerificationToken: $T" \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0" encoding="UTF-8"?><request><Control>1</Control></request>'
```

`/api/device/information` (same headers) reports the device name, firmware and
hardware version. In modem mode, `AT^RESET` on the primary port reboots the
firmware.
