# ZOWEE (Brovi) E3372-325 reference

Hardware and firmware findings from bringing up the E3372-325 with
ModemManager. Unless noted otherwise, everything was verified on firmware
`3.0.2.61(H057SP5C983)` on a Raspberry Pi 5. The [README](../README.md) covers
installation, the port layout and the patches; this document covers the rest.

## The device

The stick is sold as "Huawei E3372-325" or "Brovi E3372-325", but it isn't a
Huawei design: `ATI` reports `ZOWEE TECHNOLOGY (HEYUAN) CO., LTD.`, interface 2
calls itself `Marvell DIAG`, and the USB vendor ID is `3566`. The firmware
imitates Huawei's AT dialect, which is why ModemManager's Huawei plugin fits.
The E3372h-320 and E3372h-153 are real Huawei (HiSilicon) designs with Huawei
USB IDs.

## USB modes

The USB ID is `3566:2001` in every mode. The class of interface 0 tells the
modes apart:

| Interface 0 class | Mode | How it gets there |
|---|---|---|
| `08` | Storage (virtual CD-ROM) | After power-on or a firmware reboot |
| `e0` | HiLink (RNDIS): the stick is a router with NAT at `192.168.8.1` | HuaweiNew message (`usb_modeswitch -J`), what most guides use |
| `ff` | Modem: AT ports, diagnostics, NCM | HuaweiAlt message (`usb_modeswitch -X`, `HuaweiAltMode=1`) |

The switch isn't stored: the stick comes back in storage mode after every
power cycle and every firmware reboot, and the package's usb_modeswitch
configuration switches it again. The HuaweiAlt message also works straight
from storage mode. After `AT^RESET` the stick briefly enumerates once more
before it settles in storage mode; usb_modeswitch handles that without help.

## Modem mode interfaces

| If | Class | Endpoints | Function | Driver |
|---|---|---|---|---|
| 0 | `ff` | interrupt IN | ACM control (unused) | – |
| 1 | `ff` | bulk IN/OUT | AT + PPP | `option` |
| 2 | `ff` | bulk IN/OUT | Marvell diagnostics (not AT) | `option` |
| 3 | `ff` | interrupt IN | ACM control (unused) | – |
| 4 | `ff` | bulk IN/OUT | AT (`ATD` returns `ERROR`) | `option` |
| 5 | `02/0d` | interrupt IN | NCM control | `cdc_ncm` |
| 6 | `0a` | bulk IN/OUT | NCM data | `cdc_ncm` |

* The serial functions are two CDC-ACM pairs (0+1, 3+4) behind IADs with
  `bFunctionClass 2`, but all their interfaces have class `ff` and no CDC
  functional descriptors. `cdc_acm` can't bind them; `option` can.
* The NCM function's IAD has `bFirstInterface 0` instead of 5, so the kernel
  warns `Interface #0/#1 referenced by multiple IADs`. Harmless.
* **DTR doesn't matter.** Dialing works without ever setting DTR on interface 0
  (verified after a firmware reboot). `option` sends the line state to the data
  interface, which the stick stalls; that's harmless too.

## NCM doesn't work

`AT^NDISDUP=1,1,"<apn>"` connects (`^NDISSTATQRY` reports connected, `^DHCP?`
returns the carrier address), but the stick never sends the CDC
`NETWORK_CONNECTION` notification: a usbmon capture shows no transfer at all
on the NCM interrupt endpoint. `cdc_ncm` therefore never turns the carrier on,
and the interface stays `NO-CARRIER`. The package makes ModemManager ignore
the NCM port; data goes over PPP on interface 1.

## The firmware's attach context

After every boot and every re-attach (e.g. `AT+CFUN=4` then `AT+CFUN=1`), the
firmware defines its own context for the LTE attach at **cid 7**, and wipes
every context the host defined:

```
+CGDCONT: 7,"IP","iot.melita.io","10.0.45.157",0,0,0,0,0,0
+CGACT: 7,1
```

Dial tests with pppd (ModemManager stopped):

| Test | Result |
|---|---|
| Dial cid 7 right after the stick booted | IPCP never completes: the stick answers every Configure-Request twice (Configure-Reject and Configure-Nak); 38,057 requests in 25 s |
| `AT+CGACT=0,7`, then dial cid 7 | Deactivating fails with `+CME ERROR: 100` (it's the default bearer) |
| Define cid 1, 3 or 8 with the same APN and dial it | Works. If cid 7 is the only active context, the stick moves the default bearer onto the new cid (7 disappears, same IP) |
| Dial a second cid while a host-defined default bearer is active | Works, separate PDN connection with its own IP |
| Redial an active host-defined cid | Works |
| Dial cid 7 after a re-attach | Works |
| Dial cid 7 after a firmware reboot | IPCP loop again |

So a host-defined context always works, cid 7 only sometimes. Stock
ModemManager reuses cid 7 because its APN matches; patch 0002 hides it (udev
tag `ID_MM_HUAWEI_ATTACH_PROFILE_ID=7`), and ModemManager defines cid 1
instead. `AT+CGDCONT=0,...` fails with `+CME ERROR: 50`, so ModemManager must
not fall back to profile 0 either (patch 0002 raises the minimum to 1).

Only tested with one SIM and carrier (Melita IoT roaming on O2 Germany). If
another network leads the firmware to a different cid, the udev tag needs
changing.

## PPP and IPv6

With an IPv4v6 request (NetworkManager's default `ipv6.method=auto`), pppd
negotiates IPV6CP and the stick ends the session about 4 s after
authentication ("LCP terminated by peer"). Use `ipv6.method disabled` on the
connection.

## AT commands

Supported (used by ModemManager's Huawei plugin): `^SYSINFOEX`, `^SYSCFGEX`,
`^HCSQ=?`, `^CURC`, `^RFSWITCH?`, `^NDISDUP`, `^NDISSTATQRY?`, `^DHCP?`,
`^CARDMODE`, `^ICCID?`, `^RESET` (reboots the firmware), `+CGDCONT`, `+CGACT`,
`+CSQ`, `+CEREG`.

Unsupported or different:

| Command | Response |
|---|---|
| `^GETPORTMODE`, `^SETPORT?`, `^SETPORT=?` | `ERROR` (the package's udev rules disable `^GETPORTMODE`) |
| `^DIALMODE?` | `+CME ERROR: 50`; `^DIALMODE=?` returns `(0-2),(0-255)`, so it can be set but not read. Not tried (it's stored in the stick) |
| `^HCSQ?` | Bare `OK`. The values only come as unsolicited `^HCSQ: "LTE",<rssi>,<rsrp>,<sinr>,<rsrq>` (patch 0003) |
| `^HCSQ` | `+CME ERROR: 4` |
| `+CESQ` | `ERROR` |
| `+CFUN=1,1` | `OK`, but doesn't reboot. Use `^RESET` |
| `+CGPADDR`, `+CGEREP?`, `&V` | `ERROR` |

The stick sends unsolicited messages on the AT ports (`^RSSI`, `^HCSQ`,
`^RRCSTAT`, `^DSFLOWRPT`, `^MODE`, `^SRVST`, ...).

ASR-style commands (`+ECMDUP`, `+DIALMODE`, `+GETIP`, `+CGCONTRDP`, `+SER`)
all return `ERROR`, although ASR took over Marvell's cellular business.

## Data port recovery

After an interrupted PPP session, interface 1 stays in data mode and ignores
AT commands. `+++` with 1 s guard time before and after, then `ATH`, recovers
it; dropping DTR doesn't. ModemManager and NetworkManager handle hangups
themselves; this only matters for manual tests.

## For maintainers

### Raw AT access while ModemManager is running

Inhibit the modem to free its ports:

```sh
mmcli -m any --inhibit
```

While the command runs, interfaces 1 and 4 can be used with any serial
terminal (find the tty with `ls /sys/bus/usb/devices/<port>/<port>:1.4/`; the
`ttyUSB` numbers change with binding order). Stop it with Ctrl-C and
ModemManager takes the modem back. Without inhibiting, short queries on
interface 4 mostly work but race with ModemManager.

### Testing a change

1. Start from a clean state: `AT^RESET` reboots the stick firmware, which
   recreates the attach context (cid 7). On the Pi 5, `uhubctl` re-enumerates
   the stick but doesn't cut its power, so it doesn't reset the firmware.
2. Let NetworkManager connect and check data through `ppp0` only
   (`ping -I ppp0`), so the test doesn't depend on the host's default route.
3. Run the tests listed under [Status](../README.md#status) in the README,
   checking data after each step.
